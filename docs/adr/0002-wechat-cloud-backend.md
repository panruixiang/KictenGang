# 服务端用微信云开发，不自建

MVP 的服务端采用**微信云开发**：数据库、云函数、云存储、微信登录态全部由它提供，不自建服务器。理由是"最小版本"优先——云开发一次性免掉了域名、ICP 备案、HTTPS 证书、服务器运维这四件与产品价值无关、但会显著拖慢第一个版本的事；且 `wx.cloud` 原生携带微信身份，正好承接"厨房空间 / 成员"的共享模型。

## Considered Options

- **自建后端 + 自有数据库**：多端一视同仁、完全可控，长期路线最顺；但 MVP 阶段要额外承担备案（需要等待）、域名、证书、部署与备份。**最终未选**——Web 端已被明确排除在 MVP 之外，所以云开发"跨端别扭"这个缺点在最小版本里并不构成成本。用户一度选择此项（"用B"），随后改口为采纳推荐方案。
- **托管 BaaS（如 Supabase 一类）**：省运维、接口标准化、多端友好；但数据落在第三方，国内访问速度与合规需单独确认，未采用。

## Consequences

- 数据与身份被绑定在腾讯 / 微信生态内。若日后 Web 端成为主战场、或需要脱离微信生态，迁移成本是真实存在的。
- 有意的缓解约定：**数据访问收敛到一个独立的 `api/` 薄层**，不让云开发 SDK 散落到各个页面，使未来迁移只动一个目录而不是全项目。
- Web 端的接入路径预期为"云函数暴露 HTTP 接口 / 云托管"，而不是另起一套后端。
