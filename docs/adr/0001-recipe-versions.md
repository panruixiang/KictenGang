# 菜谱的"版本"是可编辑副本，不是不可变历史

家庭场景里同一道菜需要并存多种做法（"正常版""给孩子版"），且家人要能随时改掉其中一份、也可以直接覆盖替换掉旧的一份。因此决定：菜谱下可挂多份**可编辑、可命名、可删除、可被替换**的配方副本，术语沿用"版本"，创建时间只用于排序与展示"最近动过哪一版"。明确不做不可变的历史快照，也不做"编辑自动留历史"。

## Considered Options

- **不可变历史快照（只增不改）**：能回答"这道菜是怎么一步步演变成今天这样的"，但与用户明确要求的"替换之前的版本"直接冲突，且需要额外的历史浏览界面。
- **快照 + 可编辑副本叠加**：能力最全，但明显加厚 MVP，推迟到后续迭代。

## Consequences

- `版本` 一词在本项目里**不代表历史版本**，它等于"并存的一份配方副本"。这是有意的命名选择，见 `CONTEXT.md` 的 `_Avoid_`。
- 覆盖式"替换版本"会丢失被替换的内容——**这一点后来被修订，见下节**。

## 修订：编辑留痕改为"记"

原结论中"也不做编辑自动留历史"这一句**已被收窄**。原因是用户提出了"后续可能加上修改历史的查看"，而这与"不记录"直接冲突：

> 历史数据不记就永远补不回来。若 MVP 阶段不写日志，将来做历史查看时只能从该功能上线那天开始显示，此前的所有改动永久缺失。

因此现在的完整立场是：

- **不做的**：不可变的历史版本快照（`版本` 仍然只是可编辑副本）；修改历史的**查看界面**（不进 MVP）。
- **要做的**：**底层的变更记录从第一个版本就开始写**——每次保存菜谱或版本都追加一条记录（谁、什么时候、改了什么）。

这条修订同时缓解了上面"覆盖式替换会丢失内容"这个已接受的代价：被覆盖的改动仍留在变更记录里。
