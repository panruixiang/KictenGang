# Dev Workflow - 需求开发工作流

> ⚠️ **铁律**：文档生成完成后，**必须等待用户确认文档内容**，才能进入开发阶段。禁止在用户未确认前直接开始编码。

## 触发条件

### ✅ 应该触发的场景

当用户提到"需求"且满足以下条件之一时触发：

1. **新功能/新页面/新模块开发**（从 0 到 1）
   - "有个需求：做一个新页面"
   - "需要实现用户登录功能"
   - "新需求：数据导出功能"

2. **复杂跨模块改动**
   - 涉及 3 个以上文件的协同改动
   - 需要新增 API、状态管理、路由配置的改动
   - 需要技术方案选型（如组件封装方式、架构决策）

3. **用户明确要求走完整流程**
   - "帮我走完整流程"
   - "按需求开发流程来"

### ❌ 不应该触发的场景

以下情况**直接进入代码修改流程**，不触发 dev-workflow：

1. **Bug 修复**
   - "组件一闪而过"、"报错了"、"不显示"、"样式错乱"
   - "帮我修一下这个 bug"

2. **UI/样式微调**
   - "改一下颜色"、"调整间距"、"字体太大了"
   - "帮我优化下样式"

3. **简单的单文件逻辑改动**
   - 仅涉及 1-2 个文件的小改动
   - 文案、配置项调整

4. **用户明确说不用走流程**
   - "不用走流程，直接改"
   - "简单改一下就行"

### 边界判断逻辑

当用户说"有个需求"时，按以下优先级判断：

```
1. 先判断是否为 Bug 修复 → 看是否有"闪"、"报错"、"不显示"等问题描述
2. 再判断改动范围 → 单文件/小改动 → 不触发
3. 再判断是否为新功能 → 是 → 触发
4. 再判断复杂度 → 跨模块/多文件 → 触发
5. 其他 → 默认触发（因为用户用了"需求"这个词，通常意味着需要正式的开发流程）
```

## 工作流程

### 阶段一：文档生成（当前会话）

#### 步骤 1：调用 grill-me 完善需求

调用全局 `grill-me` skill，通过问答方式帮助用户完善需求细节：
- 引导用户描述需求背景和目标
- 询问功能细节和边界条件
- 澄清技术约束和依赖
- 补充用户故事和验收标准

#### 步骤 2：生成需求文档

将完善后的需求沉淀为需求文档，保存到 `.trae/documents/` 目录。

**文档命名规则**：AI 自动生成，格式为 `{功能名}_{日期}_需求文档.md`（中文命名，日期格式：YYYYMMDD）

**文档结构**：
```markdown
# {功能名} 需求文档

## 需求描述
- **背景**：需求产生的背景和原因
- **目标**：本次需求要达成的目标
- **范围**：需求的包含范围和不包含范围

## 功能详细设计
### 功能点 1：{功能名}
- **描述**：功能的详细描述
- **交互说明**：用户如何与功能交互
- **数据结构**：涉及的数据结构（如有）
- **页面原型**：UI 布局描述（如有）

### 功能点 2：{功能名}
...

## 技术方案（可选）
- **技术选型**：使用的技术栈
- **依赖说明**：依赖的库或服务
- **影响范围**：可能影响的模块和文件
```

#### 步骤 3：调用 to-tickets 拆解工单

基于需求文档，调用 `to-tickets` skill 将需求拆解为 **tracer-bullet 垂直切片工单**，每个工单贯穿所有层（UI、API、数据、测试），可独立演示和验证，并声明阻塞依赖（blocking edges）。

**拆解流程**：
1. to-tickets 探索代码库现状，使用项目领域术语命名
2. 起草垂直切片工单，为每个工单标注阻塞依赖（支持网状依赖，非纯线性）
3. 向用户展示工单列表（标题、阻塞依赖、交付内容），迭代直到用户批准
4. 识别广域重构（wide refactor）时，采用 expand-contract 策略单独处理

**发布方式**：用户确认后，将工单发布为本地文件，保存到 `.trae/tasks/{功能名}_{日期}/tickets/` 目录下，每个工单一个文件，按依赖顺序编号。

**工单文件命名规则**：`{NN}-{slug}.md`（如 `01-user-login.md`、`02-data-export.md`）

**工单文件结构**：
```markdown
# {NN} — {工单标题}

**What to build:** 从用户视角描述本工单实现的端到端行为

**Blocked by:** 阻塞本工单的工单编号/标题，或"None — 可立即开始"

**Status:** ready-for-agent

- [ ] 验收标准 1
- [ ] 验收标准 2
```

#### 步骤 4：生成 Checklist 文档

基于工单文件，生成可追踪的 checklist，保存到 `.trae/tasks/{功能名}_{日期}/` 目录。

**文档命名规则**：`开发checklist.md`

**文档结构**：
```markdown
# {功能名} 开发 Checklist

## 开发进度

| 工单号 | 工单标题 | 阻塞依赖 | 状态 | 备注 |
|--------|---------|---------|------|------|
| 01 | {工单标题} | 无 | ⬜ 待开始 | |
| 02 | {工单标题} | 01 | ⬜ 待开始 | |
| ... | ... | ... | ... | ... |

## 状态说明
- ⬜ 待开始：尚未开始
- 🔄 进行中：正在开发
- ✅ 已完成：开发完成，待审查
- ✓ 已确认：审查通过
- ❌ 有问题：需要修改
- ⛔ 阻塞中：等待阻塞工单完成
```

#### 步骤 5：输出文档清单并等待确认

文档生成完成后，向用户输出文档清单，然后**必须停止，等待用户确认**：

```
✅ 文档生成完成！

已创建的文档：
1. 📄 .trae/documents/{功能名}_{日期}_需求文档.md
2. 📋 .trae/tasks/{功能名}_{日期}/tickets/（包含 N 个工单文件）
3. ✅ .trae/tasks/{功能名}_{日期}/开发checklist.md

请审查以上文档，确认无误后回复"确认文档"或直接告诉我需要修改的地方。
**在你确认文档之前，我不会开始任何开发工作。**
```

> ⛔ **强制约束**：输出文档清单后，必须暂停，不得继续执行阶段二的任何步骤。只有在用户明确回复"确认文档"或"开始开发"之后，才能进入开发阶段。

---

### ⚠️ 阶段一 → 阶段二：文档确认关卡

> 这是一个**强制关卡**，不可跳过。

在进入开发阶段之前，必须满足以下**全部条件**：

1. ✅ 需求文档已生成并保存到 `.trae/documents/`
2. ✅ 工单文件已生成并保存到 `.trae/tasks/{功能名}_{日期}/tickets/`
3. ✅ Checklist 文档已生成并保存到 `.trae/tasks/{功能名}_{日期}/`
4. ✅ **用户已明确回复"确认文档"或"开始开发"**

**禁止行为**：
- ❌ 禁止在输出文档清单后自动开始编码
- ❌ 禁止假设用户默认同意文档内容
- ❌ 禁止将"用户未反对"等同于"用户已确认"
- ❌ 禁止在同一个会话中跨越阶段一和阶段二（除非用户明确确认）

**如果用户提出修改意见**：回到阶段一进行修改，修改完成后再次输出文档清单并等待确认。

---

### 阶段二：开发执行（每工单独立窗口）

每个工单在一个独立的新会话中执行，完成后提示用户开新窗口继续下一个工单，避免上下文累积导致 token 浪费。

#### 启动方式

用户在新会话中说：
- "执行 {功能名}_{日期} 的工单 {NN}"
- 或"根据 {功能名}_{日期}_需求文档 执行工单 {NN}"

AI 读取 checklist 确认该工单的阻塞依赖是否已全部完成（✓ 已确认），若未完成则告知用户需先完成阻塞工单。

#### 步骤 1：读取文档

每个窗口只读取当前工单所需的内容：
- 需求文档：`.trae/documents/{功能名}_{日期}_需求文档.md`
- 当前工单文件：`.trae/tasks/{功能名}_{日期}/tickets/{NN}-{slug}.md`
- Checklist 文档：`.trae/tasks/{功能名}_{日期}/开发checklist.md`（用于确认依赖状态和更新进度）

#### 步骤 2：执行当前工单

**2.1 开发实现**
- 按照工单描述的端到端行为实现代码
- 创建/修改所需的文件
- 按照项目的代码规范编写

**2.2 自我检查**
- 检查代码逻辑是否正确
- 检查是否符合项目规范
- 检查是否有潜在的 bug

**2.3 调用 code-review-expert 审查**
- 使用 `code-review-expert` skill 对当前工单的代码进行审查
- 如果发现 P0（Critical）或 P1（High）级别的问题，自动修复
- P2/P3 级别的问题记录下来，告知用户

**2.4 汇报进度**
向用户汇报本工单的完成情况：
```
📋 工单 {NN}：{工单标题}

✅ 开发完成
📝 代码审查：
- P0/P1 问题：{已修复 / 无}
- P2/P3 建议：{列表}

🔍 涉及文件：
- {文件路径}

⏳ 请审查代码，确认后更新进度。
```

**2.5 等待用户审查**
- 用户确认通过 → 更新文档并提示开新窗口
- 用户提出修改意见 → 修改后重新汇报

**2.6 更新文档**
用户确认后，更新：
- Checklist 文档：将当前工单标记为 `✓ 已确认`，并更新被其阻塞的工单状态（从 ⛔ 阻塞中 → ⬜ 待开始）

#### 步骤 3：提示下一个工单

当前工单确认完成后，读取 checklist 找出下一个可执行工单（阻塞依赖均已完成），向用户输出：
```
✅ 工单 {NN} 已完成并确认。

📋 下一个可执行的工单：
- 工单 {next_NN}：{工单标题}

请在新的会话窗口中执行：
"执行 {功能名}_{日期} 的工单 {next_NN}"
```

如果所有工单均已完成：
```
🎉 所有工单开发完成！

📊 完成情况统计：
- 总工单：X 个
- 已完成：X 个
- 有问题待处理：X 个（如有）

📄 进度文档：
- .trae/tasks/{功能名}_{日期}/开发checklist.md

建议进行整体测试和回归测试。
```

#### 步骤 4：处理异常情况

**如果工单执行中遇到问题**：
1. 暂停执行，告知用户遇到的问题
2. 更新 Checklist 文档，将该工单标记为 `❌ 有问题`，并在备注中说明问题
3. 询问用户如何处理

**如果需要修改之前的工单**：
1. 在新窗口中指定需要重新执行的工单编号
2. 重新执行该工单的 2.1 - 2.6 流程
3. 更新 Checklist 文档

---

## 注意事项

1. **铁律优先**：文档生成后必须等待用户确认，未确认前禁止开始编码
2. **逐条提问**：当需要向用户提问时，必须一次只问一个问题，待用户回答后再问下一个问题，禁止一次性抛出多个问题
3. **文档一致性**：确保三个文档的信息保持同步和一致
4. **代码规范**：严格遵循项目的代码规范和最佳实践
5. **审查质量**：每个步骤必须经过 code-review-expert 审查和用户确认
6. **及时更新**：遇到问题时及时更新文档，不要等到最后
7. **中文命名**：所有文档使用中文命名，符合项目习惯

## 与其他 Skill 的协作

- `grill-me`：用于阶段一的需求完善
- `to-tickets`：用于阶段一的工单拆解，将需求分解为 tracer-bullet 垂直切片工单并声明阻塞依赖
- `code-review-expert`：用于阶段二的代码审查
